# 真实账号自动生成与发布操作手册

版本：2026-09-24

客服策略的对比、风险边界和后续升级条件见[《客服回复策略方案》](客服回复策略方案.md)。

## 先给结论

目前可以用“单账号、人工确认”的方式试运行内容生产和发布准备。网页/API 服务正常，小红书专用浏览器会话当前连接到创作者中心；这证明本机登录会话可用，不代表获得了官方 API 权限。

网页已能登记账号、保存任务与内容、审核内容、准备发布草稿、导入客服消息并生成回复草稿。小红书发布中心当前只开放人工确认发布；后台可以把图文填入专用创作窗口并停在发布前，网页自动点击发布默认关闭。客服账号目前没有可识别的消息列表，因此客服页扫描已禁用。

小红书开放平台当前权限文档只列出 `basic_info` 已开放，笔记发布 `write_notes` 仍为规划中；官方 API 发布、通用创作者收件箱读取和自动回复尚未验收（见[权限说明](https://openaccount.xiaohongshu.com/docs/scope)）。大模型和 Seedance 接入不作为本轮验收条件；控制台当前显示模型“已配置，尚未实测”，本地模板只作为草稿备用。

## 小红书连接与客服页面操作

后台使用本机独立浏览器会话，不是小红书官方 API。当前小红书账号 `我想tycc / 9653254890` 的会话、登录状态和浏览器进程检查正常，页面显示“账号已连接”。这只说明专用窗口可以访问创作者中心，不代表已取得官方 API 发布权限，也不代表创作者中心提供消息入口。

账号状态按最近一次检查更新：

1. `已连接`：专用窗口可以访问创作者中心。
2. `需要重新登录`：小红书把专用窗口带回登录页；请在这个窗口扫码，密码和验证码不会保存到后台。
3. `等待连接`：后台 API 未响应，或账号专用窗口尚未连接。

当前客服按以下步骤处理：

1. 在小红书 App 或账号实际可用的官方客服工具中查看评论/私信。
2. 在后台“客服收件箱”点击“导入消息”，粘贴真实消息并选择账号、渠道和风险等级。
3. 选择会话，生成或编辑回复草稿；高风险内容转人工。
4. 点击“复制回复”，回官方工具人工发送，然后在后台登记已发送。

当前账号没有可识别的客服消息列表，所以“客服页扫描暂不可用”按钮已禁用；不要通过连续刷新或循环扫描来获取消息。后台没有定时扫描任务。手动导入的内容没有稳定的平台消息 ID，因此不能从后台定位原消息并代发；请在官方 App/客服工具中发送。登录已连接与客服入口可用是两项不同能力。

发布时，先在“内容工作室”完成审核，再在“发布中心”选择“准备小红书草稿”打开专用会话并填入图文。由你检查账号、图片、标题和正文后在官方页面手动发布，回后台登记结果。代码保留了实验性浏览器动作的隔离开关，但默认不会点击发布；只有管理员在本机显式设置 `XHS_ALLOW_EXPERIMENTAL_SUBMIT=1` 才会进入实验分支，仍不代表平台接受或发布成功。若提示账号窗口运行旧版本，先保存未完成内容、关闭该窗口，再重新打开。

## 你现在可以采用的运行模式

### 模式 A：人工辅助试运行（现在可以开始）

系统负责整理或生成内容、审核和发布准备；运营人员登录平台，核对账号、标题、正文和封面，手动发布并登记结果。小红书可以由后台填入草稿，但发布按钮由运营人员在官方页面点击。

### 模式 B：平台 Sandbox 或 Draft-only（准备好外部条件后）

系统只创建草稿或 Sandbox 对象，不公开发布。每次调用必须带新的 `trace_id`、幂等键和目标版本；平台返回未知时进入人工核查，不自动重试可能造成重复发布的请求。

### 模式 C：授权 API 自动发布（暂不可直接打开）

只有在真实 OAuth、Scope、Vault、平台适配器、健康检查、回查和 Go/No-Go 证据全部通过后，才可对指定账号启用。即使启用，也应先保持人工审批和低频上限。

### 客服回复的四条路径

| 路径 | 当前状态 | 处理方式 | 风险与适用条件 |
| --- | --- | --- | --- |
| 人工导入 + 草稿 | 当前可用，默认路径 | 从官方后台复制评论/私信，后台生成草稿，复制回官方页面发送 | 不扫描、不自动发送，最适合现在的小红书账号 |
| 官方 API / Webhook | 预留，待平台授权 | 平台推送新消息，后台校验签名后生成草稿或进入人工队列 | 需要消息 Scope、回调审核、签名校验和撤销机制 |
| 人工触发一次检查 | 预留，当前小红书入口不可验证 | 由运营人员主动打开官方页面并检查一次，不设置定时器 | 比持续轮询低风险，但只有平台页面确实提供稳定消息列表时才适用 |
| 网页自动回复 | 默认关闭 | 仅在稳定消息 ID、低风险白名单、逐条确认、冷却时间和 Kill Switch 都具备时做小流量实验 | 风控和误回复风险最高，不能作为默认运营路径 |

## 从几个真实账号开始的具体操作流程

### 第 1 步：建立账号矩阵清单

先不要把 Token 发给开发人员或放进表格。为每个账号建立一行非敏感记录：

| 字段 | 示例 | 说明 |
| --- | --- | --- |
| account_key | `brand-cn-01` | 内部稳定编号，不用平台密码或手机号 |
| platform | `platform-a` | 先选一个平台做首个平台接入 |
| external_account_id | 平台公开或授权后可回查的 ID | 只记录 ID，不记录 Token |
| owner | 账号责任人 | 负责内容和平台风险 |
| audience/locale | `zh-CN`、`en-US` | 决定语言、时区和内容变体 |
| content_pillars | 例如模型、工程、案例 | 决定选题范围 |
| publish_limit | 每日/每周上限 | 先低频，防止误发和平台风控 |
| approval_level | 人工必审/低风险可批 | 真实发布初期全部人工必审 |
| fallback | 手工导出/暂停 | 任何连接异常时的降级方式 |

账号矩阵的第一版建议只包含 1 个平台、2–3 个账号、1 个垂直主题和 1–2 种语言。矩阵扩张应该发生在单账号 Pilot 有稳定证据之后。

### 第 2 步：确认主体、授权和平台条件

每个平台至少准备以下材料，由治理负责人确认：

1. 账号所属法律主体和授权联系人。
2. 平台账号所有权证明，以及允许本项目操作的书面授权。
3. 官方开发者应用、官方 OAuth 回调地址和 Sandbox 条件。
4. 允许的 Scope 清单，并说明每个 Scope 的用途。
5. 授权有效期、撤销路径、账号交接人和紧急联系人。
6. 数据处理地区、隐私审查、平台条款和必要的 DPA。
7. 平台对象创建后的 ID 回查方法，以及未知结果的人工核查方法。

这些材料只以引用、哈希或审计记录形式进入系统；原始 Secret 只能进入批准的 Secret Manager/Vault，不能提交到代码仓库、聊天记录或 Graph State。

### 第 3 步：确认模型与存储条件（不属于本轮平台验收）

模型服务与视频生成不作为当前非模型功能的验收门槛。控制台显示模型“已配置，尚未实测”；本地模板只用于流程备用，不能据此宣称模型服务已通过生产验收。启用生产运营前仍需确认模型供应商的数据区域、保留期限、DPA 和费用预算；Seedance 与私有对象存储尚未接入。

在这一步还要准备部署托管的 PostgreSQL、任务队列/Worker、Secrets Manager、日志与告警。开发环境的 SQLite、Fake Model 和 Fake Storage 只能用于开发验收，不能当作生产并发或真实平台证据。

### 第 4 步：完成单个平台、单账号授权

授权流程按以下顺序执行：

1. 管理员创建授权会话，绑定组织、平台、账号用途、Scope、回调地址和过期时间。
2. 系统生成一次性 OAuth State 和 PKCE challenge；State 只保存哈希或引用。
3. 运营人员在官方页面授权，不把回调参数复制到聊天工具。
4. 回调只完成授权和 AccountConnection 建立，不触发发布。
5. 系统校验 State、PKCE、精确回调地址、Scope 和授权期限。
6. 原始 Token 进入 Vault；业务数据库只保存 secret reference、租约状态、Scope 快照和审计引用。
7. 立即执行连接健康检查、平台账号 ID 回查和能力矩阵检查。
8. 首次只启用 `draft_only` 或 `manual_export`；健康检查失败就进入 restricted 状态。

### 第 5 步：生成一条内容并完成审批

每一条内容都按同一个流水线执行：

1. 输入选题、受众、语言、账号目标和第一方证据引用。
2. 生成内容草稿和账号变体；Graph State 只保存引用，不保存 Token、完整正文、PII 或二进制。
3. 执行来源、版权、事实、敏感内容、提示注入、格式和平台规则检查。
4. 生成 QA 结果、风险等级、模型调用审计和成本记录。
5. 人工审核人确认内容、目标账号、发布时间、媒体和免责声明。
6. 如果审核人修改了正文、目标账号或发布时间，必须重新执行受影响的检查。
7. 形成不可变的内容版本和发布意图；发布意图必须绑定组织、账号、Policy 快照和幂等键。

### 第 6 步：执行人工导出或 Sandbox 草稿

当前推荐使用人工导出：

1. 系统导出每个账号的最终文本、媒体引用、标题、标签、语言和发布时间。
2. 运营人员登录官方平台，核对账号头像、组织、平台页面和可见权限。
3. 手动粘贴/上传并保存平台草稿或发布结果。
4. 把平台对象 ID、最终 URL、发布时间、截图/回执引用登记回系统。
5. 如果平台显示失败但无法确认是否创建成功，立即停止重试，进入未知结果核查。

若已经具备 Sandbox，则把第 2–4 步替换为 Draft-only API 调用，但仍要保留平台返回 ID、请求幂等键、Scope 快照和回查结果。

### 第 7 步：小流量试点和账号矩阵扩展

首个 Pilot 建议使用 1 个账号、每天 1–2 条、连续 2–4 周，设置明确的暂停条件：连接健康失败、重复发布、版权投诉、模型输出异常、平台告警、成本超阈值或人工审核积压。

每周复核授权期限、Token 租约、Scope 变化、失败任务、未知结果、投诉、内容质量、成本、平台健康和 GEO/反馈波动。只有单账号证据稳定，才复制到第二个账号；每复制一个账号都要有独立能力矩阵、责任人和回滚方式。

## 发布时必须遵守的控制点

- 不在 Graph State、日志、事件、审计或导出文件中保存原始 Token。
- 不把一个账号的内容、授权或平台对象泄露给同租户的另一个账号。
- 每次写操作使用新的幂等键；网络超时后先回查，不直接重试。
- 只允许已批准 Scope 和能力矩阵内的动作；Scope 改变必须重新授权和复核。
- 发布执行人与审批人分离；真实账号初期全部人工审批。
- Kill Switch 可以在排队、平台调用和结果回查前阻断发布。
- 任何未知外部结果进入人工核查；禁止用“看起来失败”推断没有发布。
- 账号健康、授权期限、Vault 租约或平台权限异常时自动降级为 restricted/manual_export。

## 还需要你提供什么

### 每个平台/账号

- 法律主体、授权联系人和账号责任人。
- 平台名称、账号公开信息、external account ID 和所属组织。
- 官方开发者应用/Sandbox 资格、精确回调地址和批准 Scope。
- 平台条款、内容政策、隐私和数据区域要求。
- 平台对象创建后的 ID 回查与删除/撤销流程。
- 每日/每周发布上限、内容栏目、语言、时区和暂停条件。

### 运行基础设施

- 批准的模型供应商、区域、DPA、保留期限和费用预算。
- Secret Manager/Vault、托管 PostgreSQL、私有对象存储和备份策略。
- Worker/队列、告警渠道、值班负责人和事故升级路径。
- 第一平台的官方 API 文档、测试账号和 Sandbox 回执。

### 验收证据

- authorization record
- scope snapshot
- connection health check
- external ID and re-query result
- sandbox/draft-only response
- provider idempotency result
- revoke/expiry/kill-switch drill
- 未知结果人工对账记录

## 建议的后续开发顺序

1. 选定一个官方平台和一个试点账号，补齐 `EXT-ACCOUNT-001` 的证据。
2. 完成该平台独立的 OAuth Provider、官方适配器和能力矩阵，先只支持 Draft-only。
3. 部署 Vault、PostgreSQL、对象存储、Worker、日志和告警，并完成生产组合测试。
4. 运行单账号 2–4 周 Pilot，形成质量、成本、健康、投诉和回滚证据。
5. 通过 Go/No-Go 后再打开授权 API 发布；随后逐个复制到账号矩阵。

在上述证据齐全前，项目可以作为单账号内容生产、发布准备和人工客服草稿工具使用。小红书浏览器只做受控的草稿填入，自动提交和自动客服回复默认关闭；不应对外宣称可靠的无人值守自动发布、自动客服回复或规模化账号矩阵运营已完成。
