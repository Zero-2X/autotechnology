## 1. 审计结论

V2.4 可以作为项目的开发规划基线，整体架构方向合理，适合在没有真实平台账号的情况下先建设核心内容生产系统。核心链路已经明确为：

```text
TopicSignal → TopicOpportunity → TopicBrief
→ Source/Rights → KnowledgeCore → CanonicalContent
→ Variant → QA/Policy/Approval
→ Manual Export/Fake Adapter → Observation → Feedback
```

账号后置方案可行且科学。平台账号、OAuth、Token Vault、账号健康、平台 Webhook 和真实适配器属于 Distribution Layer，不能阻塞无账号阶段的内容、知识、质量、审批和手工导出能力。内部 IAM、组织上下文、角色权限、审计、Kill Switch 和策略门禁仍必须前置。

当前只能称为 **Account-free Architecture MVP（无账号架构 MVP）**，不能宣称已经具备真实平台发布能力，也不能把 Fake、人工导入或模拟结果标记为真实平台指标。

本轮还把交付范围拆成两层：`M1-Core` 只要求无账号文本纵向切片和 Manual/Fake 分发，`M1-Plus` 再加入第一方知识站、GEO、Media/Asset 和离线评测。这样可选能力不会阻塞核心架构或后续账号接入。

## 3. 目录和可维护性审计

推荐的顶层边界是合理的：`apps` 负责进程入口，`modules` 负责领域逻辑，`adapters` 负责外部实现，`packages/contracts` 负责机器契约，`packages/db` 负责数据库基础能力，`tests` 按测试类型分层，`docs/tasks` 负责单任务说明。

每个 `modules/<module>/` 应保持统一内部结构：

```text
README.md
domain/
application/
ports/
infrastructure/
projections/
```

维护时必须遵守以下边界：

- 领域规则不能依赖 FastAPI、ORM 或平台 SDK。
- API、Worker、Scheduler 只做入口、依赖装配、租约和用例调用。
- Adapter 只能实现已登记的 Port，供应商类型不能泄漏到领域模型和公共事件。
- Projection 是可重建读模型，不是第二个事实源。
- 跨模块写入必须经过公开用例、命令或事件，不能直接写他人表。
- 目录移动、模块改名和跨模块依赖变化必须先更新 ADR、任务注册表和模块 README。

这套规则能够降低后续修改时的影响范围，也能让 Codex 根据 `allowed_paths` 找到唯一修改位置。

## 4. 账号后置工作流审计

无账号阶段使用 `planned` 或 `synthetic` 的账号引用对象，TargetVersion 只允许 `manual_export` 和 `simulation`。真实账号接入必须创建新的不可变 TargetVersion 和新的、带 `derived_from_intent_id` 的 PublicationIntent，不能回写历史对象。

推荐的账号迁移顺序是：

```text
EXT-ACCOUNT-001 满足
→ 授权证据登记
→ AccountConnection 建立
→ Scope/健康/区域/能力检查
→ 新建真实 TargetVersion
→ 重算 PolicySnapshot/PolicyDecision
→ 创建新的 PublicationIntent
→ 先开放 draft_only
→ 外部回查确认
→ 低频受控发布
```

队列领取、平台调用和回查前都必须重新检查 Kill Switch、Scope、账号健康和 Policy。未知结果只能进入查询和人工确认，不得自动重试创建外部对象。Token 只能保存在 Secret Manager/KMS，数据库和日志只能保留脱敏快照、Scope 哈希、版本和证据引用。

## 5. 当前阻塞项和下一步

进入业务实现前必须完成：

1. 完成 `FOUND-000` 仓库清点和阶段 0 的范围、Owner、RACI、SLO、RPO/RTO、预算及外部依赖填写；当前首个技术垂直领域仍是 `[VERTICAL_REQUIRED]` 占位符。
2. 优先细化 M1-P0 任务卡，尤其是底座、IAM、无凭证 Target、Workflow、Model/Agent、Topic、Provenance、Knowledge、Canonical、Production、QA、Policy、Approval 和 Distribution 任务。
3. 将当前基线 Schema 逐项与具体任务和对象对齐，避免使用过于宽泛的兼容文件名。
4. 每个任务进入 `in_progress` 时创建自己的正式 Alembic revision；`planned` 阶段只保留表范围和规划路径，任务到 `done` 前必须在临时数据库完成升级、验证和回滚证据。
5. 运行状态机、事件、API 和租户隔离的闭环审计。
6. 账号到位后才执行 OAuth、Vault、真实 Webhook、真实平台适配器和真实指标验证。

Codex 每次只执行一个 `TASK-ID`，先读取任务卡、模块 README、ADR、契约、迁移和当前工作树；先更新契约/迁移/测试，再实现代码。依赖或验收条件不完整时，应报告具体阻塞项，不跨阶段补功能。

本轮审计还修正了 P0 依赖方向：P0 不再依赖可选 Redis、Scheduler、Transform Agent、SBOM 签名或平台配额任务。任何新的 P0→P1/M2/M3 依赖都会由一致性脚本判为错误。任务卡精细化采用增量门禁：全量报告可以显示未细化卡片，但 Codex 只需在执行某个任务前通过 `check_task_card_precision.py --task <TASK-ID> --strict`，不必等待全部 92 个 P0 卡片完成。
